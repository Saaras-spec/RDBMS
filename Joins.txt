JOINS in SQL

In a relational database, data is intentionally split into separate tables to avoid duplication (this is called Normalization).
JOINS are the glue that puts that data back together when you need to read it.
In SDE interviews at product companies, JOINS are not just tested -- they are the foundation of almost every live-coding SQL question.

The Scenario

Imagine you have two tables.
Users Table: Holds the user_id and name.
Orders Table: Holds the order_id, amount, and the user_id of the person who bought it.

Users
user_id | name
1       | Sanjana
2       | Alice
3       | Bob
4       | Charlie

Orders
order_id | user_id | amount
101      | 1       | 250
102      | 1       | 500
103      | 2       | 300
104      | 5       | 200

Notice that some users haven't bought anything, and some orders belong to deleted users.

1. INNER JOIN (The Strict Match)

An INNER JOIN acts like a strict bouncer. It looks at both tables and only keeps the rows where there is an exact match on both sides.
Result: You only get Users who have actually placed an Order.

Users                  Orders
Only matching rows

SQL:

SELECT Users.name, Orders.amount
FROM Users
INNER JOIN Orders
  ON Users.user_id = Orders.user_id;

Output:

name     | amount
Sanjana  | 250
Sanjana  | 500
Alice    | 300


2. LEFT JOIN (The Most Tested Join)

A LEFT JOIN grabs every single row from the Left table (the one written first), regardless of whether it finds a match in the Right table.
If it finds a match, it attaches the data. If it doesn't, it just attaches NULL.
Result: You get ALL Users. If they bought something, you see the amount. If they didn't, their amount shows as NULL.

Users                  Orders
All rows from left table

SQL:

SELECT Users.name, Orders.amount
FROM Users
LEFT JOIN Orders
  ON Users.user_id = Orders.user_id;

Output:

name     | amount
Sanjana  | 250
Sanjana  | 500
Alice    | 300
Bob      | NULL
Charlie  | NULL

The SDE Interview Question: "Find all users who have NEVER placed an order."
The SDE Answer: You use a LEFT JOIN to grab everyone, and then use a WHERE clause to filter for the NULL values that the LEFT JOIN created!

SQL:

SELECT Users.name
FROM Users
LEFT JOIN Orders ON Users.user_id = Orders.user_id
WHERE Orders.order_id IS NULL;  -- The magic filter


3. RIGHT JOIN (The Flipped Left Join)

It does the exact same thing as a LEFT JOIN, but backwards. It grabs everything from the Right table, and NULL for missing Left data.
Result: You get ALL Orders. If the user was deleted, the user's name shows as NULL.
SDE Angle: In professional backend code, we almost never use RIGHT JOIN. It forces engineers to read queries backwards. Instead of using a RIGHT JOIN, we simply swap the order of the tables and use a LEFT JOIN. All rows from right table

Users                  Orders

SQL:

SELECT Users.name, Orders.amount
FROM Users
RIGHT JOIN Orders
  ON Users.user_id = Orders.user_id;

Output:

name     | amount
Sanjana  | 250
Sanjana  | 500
Alice    | 300
NULL     | 200


4. FULL OUTER JOIN (The Everything Join)

This grabs absolutely everything. If there's a match, it connects them.
If a User has no Order, they get NULL. If an Order has no User, it gets NULL.

Users                  Orders
All rows from both tables

SQL:

SELECT Users.name, Orders.amount
FROM Users
FULL OUTER JOIN Orders
  ON Users.user_id = Orders.user_id;

Output:

name     | amount
Sanjana  | 250
Sanjana  | 500
Alice    | 300
Bob      | NULL
Charlie  | NULL
NULL     | 200

The Ultimate SDE Trap: "The Fan-Out Effect"

The Question: "Table A has a user named Sanjana (ID 1). Table B has three separate orders that all belong to User ID 1. If we INNER JOIN them, how many rows are returned?"

The SDE Answer: "It returns THREE rows. A JOIN does not squash data; it multiplies it. The database takes Sanjana's single row from Table A and duplicates it three times to attach it to all three distinct orders in Table B. This is called a 'One-to-Many' fan-out. If we aren't careful, joining multiple One-to-Many tables together can accidentally explode our output into thousands of duplicated rows, crashing the query."


5. CROSS JOIN (The Cartesian Product)

A CROSS JOIN takes every single row from the first table and pairs it with every single row from the second table. This is mathematically known as a Cartesian Product.
Unlike other JOINs, a CROSS JOIN does not use an ON clause because it is not looking for a matching ID. It simply forces a combination of everything.

The SDE Interview Angle:

When do we actually use this?
If you say "I use a CROSS JOIN to combine tables," the interviewer will ask: "Wouldn't that crash a production database?"

The SDE Answer:

"Yes, a CROSS JOIN on two tables with just 10,000 rows each results in 100 million rows, which can easily cause an OOM crash. We almost never use it for standard data retrieval. However, it is a crucial tool for Gap Filling in Analytics.

For example, to show user activity for every single day of the month, I would do a CROSS JOIN between a list of all Users and a list of all 30 Dates to create a perfect matrix. Then, I would LEFT JOIN the actual activity data onto that matrix so days with no activity show up with a safe 0 instead of disappearing from the graph."

Table 1: Colors

color_name
Red
Blue

Table 2: Sizes

size_name
Small
Large

SQL:

SELECT Colors.color_name, Sizes.size_name
FROM Colors
CROSS JOIN Sizes;

Output:

color_name | size_name
Red        | Small
Red        | Large
Blue       | Small
Blue       | Large
