DDL vs. DML vs. DQL (The Developer Suite)

These three categories are what you will write on a daily basis as a software engineer.

1. DDL (Data Definition Language)

DDL commands build and modify the schema (the blueprint). They dictate the structure of the tables, not the data inside them.

Commands:
CREATE, ALTER, DROP, TRUNCATE.


2. DML (Data Manipulation Language)

DML commands modify the actual records stored inside those structures.

Commands:
INSERT, UPDATE, DELETE.


3. DQL (Data Query Language)

DQL is dedicated entirely to fetching and reading data without changing it.

Commands:
SELECT.


SDE Interview Note:

Many older university textbooks group SELECT under DML. However, in modern backend engineering, SELECT is strictly considered DQL because it performs a "Read" (which is safe and non-destructive), whereas DML performs "Writes" (which alter the database state).


Part 2: TCL vs. DCL (The Safety & Security Suite)

You will use these to ensure the database doesn't break during system failures and to manage who gets to see what.


4. TCL (Transaction Control Language)

TCL commands manage transactions. A transaction is a bundle of DML commands (Inserts/Updates/Deletes) that must all succeed together or all fail together.

Commands:

COMMIT:
Permanently saves the transaction to the database.

ROLLBACK:
Cancels the transaction and undoes any changes if an error occurs halfway through.

SAVEPOINT:
Creates a temporary checkpoint you can roll back to without canceling the entire transaction.


5. DCL (Data Control Language)

DCL commands manage security, roles, and permissions.

Commands:

GRANT:
Gives a user permission to do something (e.g., GRANT SELECT ON Users TO analytics_team;).

REVOKE:
Takes that permission away.


The Interview Angle: The "Bank Transfer" Scenario

Product-based companies care deeply about TCL because it relates to system reliability. If an interviewer asks, "Why do we need TCL commands?", use this classic SDE answer:

The SDE Answer:

"TCL commands protect data integrity during system failures. Imagine a bank transfer where we deduct $100 from Alice (Update 1) and add $100 to Bob (Update 2). If the database server crashes exactly between Update 1 and Update 2, Alice loses $100, but Bob never gets it. By wrapping both updates in a single Transaction, we ensure safety. If the server crashes, the database automatically performs a ROLLBACK to undo Alice's deduction. If both succeed, we COMMIT the changes permanently. This is the foundation of ACID compliance."
